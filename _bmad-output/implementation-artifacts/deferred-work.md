# Deferred Work Ledger

## Deferred from: code review of 1-6-yolk-spit-weapon (2026-09-19)

- `top_level = true` decouples a projectile's transform but NOT its visibility, modulate, z-order, light mask or material: a CanvasItem still inherits all of those through its parent chain, which here runs projectile -> Weapon -> Player. So `projectile.visible = true` in `launch()` is conditional on the whole Player chain being visible, and because the pool's real availability flag (`is_active`) is deliberately decoupled from `visible`, any mismatch fails silently. Concretely, the hit feedback Story 1.4 still owes (conventionally a blinking `modulate` or `visible` on the Player) would blink every in-flight projectile with it; a death fade or `hide()` on the Player in Epic 5 would make live, still-colliding projectiles invisible; and setting `process_mode = DISABLED` on the Player at game over would freeze projectiles mid-air while they remain visible and monitoring. Nothing does any of these today. Story 1.6's Dev Notes justified parenting the pool under the weapon as "frees them with the Player" without noting the inheritance. Revisit when Epic 5 adds hit feedback or a game-over state; the alternative is reparenting the pool to the scene root, which trades this away for a cross-feature reference.
- Story 1.8 (projectile damage) has no detection path from the enemy side. The enemy `HurtBox` added by Story 1.6 is script-less with `monitoring = false` and `collision_mask = 0`, and `ProjectileBase` is `collision_layer = 0` with `monitorable = false`, so detection runs strictly one way (projectile sees hurtbox) and an enemy can never learn it was hit. `ProjectileBase._on_area_entered(_area: Area2D)` also discards the only handle to the victim, and `weapon_hit(enemy, damage)` was deliberately left off `SignalBus`. Story 1.8 therefore cannot simply "attach damage handling to the HurtBox"; it must pick one of: (a) `_area.get_parent().take_damage(...)`, a direct `features/weapons` to `features/enemies` reference that AGENTS.md's Communication Rule forbids; (b) flip the HurtBox to `monitoring = true` with a mask covering a new projectile layer, undoing three values Story 1.6 shipped across two hand-synced enemy scenes; or (c) add a bus signal carrying enemy identity, which no existing signal has. Decide deliberately at the start of 1.8 rather than discovering it mid-implementation.
- The first shot's collision detection depends on Godot MessageQueue flush ordering rather than explicit sequencing, and `fire_rate` is latched at `_ready()`. `WeaponBase._ready()` queues `_fire_first_shot.call_deferred()` before `ProjectileWeapon._ready()` has built the pool, so the pool's 16 deferred `monitoring = false` calls are queued after it; the launched projectile ends up monitoring only because `launch()` also defers its `monitoring = true`, which lands last. All three review layers verified this resolves correctly, but the correctness is implicit and a reordering would break it silently. Separately, `_fire_timer.wait_time = 1.0 / stats.fire_rate` is computed once, so mutating `fire_rate` on the (deliberately `resource_local_to_scene`) stat sheet at runtime does nothing. Resolve both together when Epic 4 adds weapon upgrades: validate, then build the pool through an overridable setup hook, then queue the first shot, and re-read `fire_rate` when it changes. Both alter verified-working startup behaviour and need a fresh manual run.

## Deferred from: code review of 1-5-player-health-system (2026-09-19)

- Death state latches with no reset path anywhere in code. `Player._is_dead`, `PlayerHurtBox._player_dead` and `GameManager.is_game_over` are all set on death and never cleared, and `current_health` only ever decreases. `GameManager.start_game()` does reset `is_game_over` and `score`/`current_wave`, but it has zero callers project-wide. Consequences for whoever builds restart: an in-place restart (calling `start_game()` without reloading the scene) leaves the player alive-but-dead - frozen, invulnerable, unable to die again, with the run unplayable and unloseable; conversely a `reload_current_scene()` restart that forgets `start_game()` carries `is_game_over == true` plus stale score and wave into a fresh run whose Player is alive, a split-brain state. Deferred because restart and game-over flow are Epic 5 scope (E5-S4) and Story 1.5 deliberately built no restart. Whoever owns E5-S4 must either call `start_game()` as part of a full scene reload, or add explicit reset paths (`Player` restoring `current_health` and clearing `_is_dead`, `PlayerHurtBox` clearing `_player_dead` AND `_pending_damage`).
- Health routing over the global `SignalBus` silently assumes exactly one Player. Every `Player` connects `take_damage` to the global `player_damaged` and every `PlayerHurtBox` emits into it, so with two live instances each Player applies both emissions (double damage), `player_health_changed` interleaves two senders with no identity payload, and `player_died` fires twice - contradicting the "emitted exactly once" contract documented on the signal. The `_is_dead` guard is per-instance and structurally cannot protect a global signal. Deferred because `features/gameplay/arena.tscn` instances exactly one Player and nothing today creates a second. Becomes reachable if Epic 5's restart instances a new player before freeing the old (`add_child` then `queue_free` leaves both live until end of frame, which `change_scene_to_*` avoids), or if a decoy/clone upgrade is ever added. Resolve by adding sender identity to the player signals or routing damage per-instance rather than over the bus.

## Deferred from: code review of 1-4-enemy-player-contact-damage (2026-09-19)

- **RESOLVED by Story 1.5 (2026-09-19):** `PlayerHurtBox` stops resolving damage after `player_died`, and `GameManager.is_game_over` is now set on `player_died`. Original entry: No game-over gating on contact damage. `GameManager.is_game_over` exists and is written in `start_game()` but read by nothing. Once Story 1.5 lands player death, enemies stay parked on the player (`arrival_distance` keeps them there, and nothing despawns them at game over), so `SignalBus.player_damaged` keeps firing once per second forever, driving HP negative and potentially re-entering death handling. Deferred because `is_game_over` is never set true yet, making a check speculative today. Story 1.5 owns death and should wire this — either an `is_game_over` check in `PlayerHurtBox`, or disabling the HurtBox on death.
- The arrival-distance stop behaviour lives on `SpermCell` (`features/enemies/sperm_cell.gd`), not on `EnemyBase`, so every future enemy type that overrides `_get_move_direction()` re-introduces the on-top-of-the-player jitter Story 1.4 just closed — and it now matters more, because jitter moves an enemy in and out of the 22px contact band and so flickers contact damage. Additionally, the invariant "keep `arrival_distance` below the HitBox + HurtBox range (14 + 8 = 22)" exists only as a doc comment on an `@export` field, so any instance value at or above 22 yields an enemy that charges, parks just outside contact range, and deals zero damage with no error. Deferred because Story 1.4 Task 4 explicitly forbade changing `enemy_base.gd` and nothing sets a value near 22 today. Revisit when Epic 2 (Story 2.6) adds the second enemy type: hoist the stop check into `EnemyBase` and clamp or derive the distance from the hitbox radius.
- Per-frame signal emission scales with enemy count: every overlapping enemy emits `enemy_reached_player` each physics frame and all but the first are discarded by the player-side gate (roughly 50 dispatches per frame with a large pile-up, 49 of them hitting an early return). Deferred as already nominated in Story 1.4's Testing Requirements: Story 2.1 (wave spawner) is the place to switch to `area_entered`/`area_exited` tracking if profiling shows real cost.
- `roundi(stats.damage)` in `features/enemies/enemy_hit_box.gd` floors any damage below 0.5 to 0, and the player-side gate consumes the full invulnerability window before inspecting the value — so a 0-damage enemy would act as a shield, absorbing each window and blocking real hits. Deferred: unreachable today (no enemy has damage below 0.5); becomes reachable only if difficulty scaling ever multiplies damage downward.

## Deferred from: code review of 1-3-spermcell-charge-enemy (2026-09-19)

- `features/enemies/sperm_cell.tscn` duplicates `features/enemies/enemy_base.tscn`'s node structure (root type, `motion_mode`, collision layer/mask, shape radius, child nodes) instead of being a Godot Inherited Scene, leaving the base scene as an unused template that will silently drift as shared changes (hurtbox, layers, shape) get added per-enemy in Epic 2. Deliberate: hand-authoring inherited-scene `.tscn` format outside the Godot editor is error-prone, and Story 1.3 had no editor access. Story 1.3's Task 4 explicitly required this tradeoff be flagged to the user rather than treated as final architecture — that flag was missed at hand-off, and this entry corrects it. Resolution options: convert via the editor's "New Inherited Scene", or drop `enemy_base.tscn` entirely and rely on base-*script* inheritance only.
- Enemies neither collide with nor separate from each other (`collision_mask = 1` covers `world` only), so multiple spawns will stack into a single overlapping blob. Not observable with Story 1.3's single hand-placed enemy. Becomes real in Story 2.1 (wave spawner), which is the right place to choose between mask-based separation and a steering/separation behaviour.
- **RESOLVED by Story 1.4 (2026-09-19):** `SpermCell` now has `arrival_distance = 10.0` and stops moving inside it. Original entry: No arrival/stop distance in `features/enemies/sperm_cell.gd`: the direction vector returns `Vector2.ZERO` at exact overlap and can oscillate under float noise near zero, so an enemy that reaches the player jitters on top of them. Cosmetic today, since enemies pass through the player harmlessly by design (Story 1.3 AC #4). Tune once Story 1.4 adds contact damage and there is real behaviour to tune against.

## Deferred from: code review of 1-1-player-movement (2026-09-18)

- Arrow keys are double-bound to `move_*` (this story) and Godot's built-in `ui_up`/`ui_down`/`ui_left`/`ui_right` actions in `project.godot`. Once any UI has focus (pause menu, level-up cards, main menu), arrow-key presses will simultaneously move the player and shift UI focus/navigation. Logged for Epic 5 (UI & Menus): decide there whether to unbind arrows from `ui_*` or gate `move_*` input by game state.
- No gamepad/joypad events bound on `move_*` actions in `project.godot` (only keyboard); the `deadzone: 0.5` field is currently meaningless since no analog input is bound. Pre-existing scope boundary — gamepad support has no story yet in the epics backlog.
- `velocity = input_vector.normalized() * speed` in `features/player_egg/player.gd:9` re-normalizes an already magnitude-clamped `Input.get_vector()` result, forcing full speed regardless of input magnitude. Harmless for keyboard-only input (always magnitude 0 or 1); only matters once gamepad/analog input is added.
- No explicit `collision_layer`/`collision_mask` set on the player (`features/player_egg/player_egg.tscn`); relies on Godot defaults. No other physics bodies exist yet (arena boundaries land in E1-S2, enemies in E1-S3) to define a layer convention against.
- Collision shape radius (16px) on the player (`features/player_egg/player_egg.tscn`) is a guess with no player art yet to validate it against. No art assets exist in the project yet.
