# Story 1.6: Basic auto-attack weapon (Yolk Spit)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want my egg to fire yolk globs on its own at a steady rate,
so that I have an attack to build on while I focus on dodging.

## Acceptance Criteria

The epics file gives this story no criteria of its own (only the epic-level line "Weapon auto-fires at nearest enemy", which is S7's job). These were settled by story creation from the user's five decisions, the sprint-status task list, and the architecture doc.

1. **`WeaponStats` resource.** `core/data/weapon_stats.gd` defines `class_name WeaponStats extends StatsResource` with **exactly** the fields in game-architecture.md#WeaponStats and no others: `weapon_name: String = ""`, `weapon_type: String = "projectile"`, `base_damage: float = 10.0`, `fire_rate: float = 1.0`, `projectile_count: int = 1`, `spread_angle: float = 0.0`, `piercing: int = 0`, `area_multiplier: float = 1.0`, `knockback: float = 0.0`, `projectile_scene: PackedScene`. Only `weapon_name`, `fire_rate`, `projectile_scene` and the inherited `speed` are read in this story; every other field is inert. [Source: game-architecture.md#WeaponStats; AGENTS.md "extend StatsResource"; Story 1.3 precedent of following documented field lists exactly]
2. **Yolk Spit is configuration, not a subclass.** A `WeaponStats` resource embedded in `player_egg.tscn` configures it: `weapon_name = "Yolk Spit"`, `weapon_type = "projectile"`, `fire_rate = 1.0` (one shot per second, per gdd.md "attacks per second"), `speed = 400.0` (the inherited `StatsResource.speed`, used as **projectile** speed), `base_damage = 10.0` (inert), `projectile_scene` = `projectile_base.tscn`, and `resource_local_to_scene = true`. [Source: gdd.md#Weapons; user decision; Story 1.3 "no empty subclass"]
3. **`WeaponBase`.** `features/weapons/weapon_base.gd` (`class_name WeaponBase extends Node2D`) exports `stats: WeaponStats`, owns a `FireTimer` (`Timer`) whose `wait_time` is `1.0 / stats.fire_rate`, fires **once immediately** when the weapon starts (so an auto-attack is not silent for a full interval; added by user instruction 2026-09-19), then on each `timeout` calls an overridable `_fire()` (a no-op in the base). It never fires when `stats` is null, `fire_rate <= 0.0`, or `projectile_scene` is null: it logs one `push_error` and stays inert instead of crashing or dividing by zero. [Source: architecture#Weapons; Story 1.5 lesson on misconfigured stats]
4. **`ProjectileWeapon`.** `features/weapons/projectile_weapon.gd` (`class_name ProjectileWeapon extends WeaponBase`) overrides `_fire()`: it takes a projectile from its pool, launches it from the weapon's own `global_position` in the fixed direction `Vector2.RIGHT` at `stats.speed`, and emits `SignalBus.weapon_fired(weapon_name, position)`. **No targeting, aiming, facing or nearest-enemy logic of any kind.** [Source: user decision 1]
5. **Composition, not references.** `features/weapons/projectile_weapon.tscn` is a dedicated scene that owns `projectile_weapon.gd` (scene name = script identity), with the same node structure as `weapon_base.tscn` (root `Node2D`, child `FireTimer`). `player_egg.tscn` instances **`projectile_weapon.tscn`** as a child node of `Player`, named `Weapon`, and assigns the embedded stats. `weapon_base.tscn` stays as the abstract base scene, unused for now, and is **not** instanced anywhere and **not** script-overridden. `player.gd` is **unchanged**. The weapon reads no Player state: no `get_parent()`, no group lookup, no reference to `Player` or `player.gd`. [Source: user decision 4, amended by the user on 2026-09-19 to reject a script override on `weapon_base.tscn`; AGENTS.md Communication Rule]
6. **Projectile.** `features/weapons/projectile_base.tscn` is an `Area2D` (`class_name ProjectileBase`, script `projectile_base.gd`) with `CollisionShape2D` (circle, radius 5), a textureless `Sprite2D` placeholder, and a `LifetimeTimer` (`Timer`, `one_shot`, `wait_time = 2.0`). `top_level = true` (so it ignores its parent's transform), `collision_layer = 0`, `collision_mask = 16` (layer 5 `enemy_hurtbox`), `monitoring = true`, `monitorable = false`. When launched it moves in a straight line at the given speed. It is released back to the pool when its `LifetimeTimer` fires **or** when it overlaps a layer-5 area. It applies **no damage** and emits **no `weapon_hit`**. [Source: user decision 2; architecture#Projectiles]
7. **Pooling, this projectile type only.** `ProjectileWeapon` pre-instantiates a fixed-size pool (`@export var pool_size: int = 16`) at `_ready()`. Pooled-but-inactive projectiles are hidden, have `_physics_process` disabled, `monitoring` off and their timer stopped. Fired projectiles are reused after release; nothing is `instantiate()`d or `queue_free()`d during play. If the pool is exhausted the shot is skipped and **one** `push_warning` is logged (not one per shot). The pool is not a generic multi-type framework and is not an autoload. [Source: user decision 3; game-architecture.md#Object Pooling]
8. **Enemy HurtBox (bare).** `enemy_base.tscn` and `sperm_cell.tscn` each gain a child `Area2D` named `HurtBox` with a circle `CollisionShape2D` (radius 12, matching the body): `collision_layer = 16` (layer 5), `collision_mask = 0`, `monitoring = false`, `monitorable = true`. **No script and no behaviour**: it exists only so the projectile has something on layer 5 to detect. Damage handling is S8. (Flagged, see Dev Notes.) [Source: game-architecture.md#Enemies node structure]
9. **SignalBus.** `signal weapon_fired(weapon_name: String, position: Vector2)` is added (signature per game-architecture.md). `weapon_hit` is **not** added. [Source: user decision 5]
10. **No firing after death.** `WeaponBase` connects to `SignalBus.player_died` and stops its `FireTimer`. Projectiles already in flight finish their life normally. [Source: Story 1.5 review; a dead player must not keep attacking]
11. **Scope held.** No targeting/aiming/facing (S7), no damage/`weapon_hit`/enemy health/despawn-on-death (S8, S9), no `WeaponPivot`, no weapon `Sprite2D`, no weapon slots, upgrades, evolution, spread, piercing, knockback, `projectile_count > 1`, HUD, VFX or audio, and **no change to enemy behaviour or to `player.gd`**. Stories 1.3-1.5 behaviour is preserved: one `player_damaged` per about 1 s under contact, `player_died` exactly once, input frozen after death.
12. The arena runs without console errors or warnings.

### Review Findings

- [x] [Review][Decision] **Resolved 2026-09-19: offset the spawn along the fire direction.** `ProjectileWeapon` gained `@export var muzzle_offset: float = 20.0` (enemy hurtbox 12 + projectile 5, plus margin) and launches from `global_position + direction * muzzle_offset`. `weapon_fired` still reports the weapon's own position. Known tradeoff accepted: at point-blank range a shot can now skip over an enemy sitting between the player and the muzzle point. Original finding: Every shot is eaten at the muzzle whenever an enemy is touching the player. The projectile spawns at the `Weapon` node's `global_position`, which has no offset, so it starts at the player's centre. A SpermCell parks at `arrival_distance = 10.0` from that centre, its HurtBox radius is 12 and the projectile's is 5, so the overlap threshold is 17px and the enemy is already well inside it. When `launch()`'s deferred `monitoring = true` flushes, Godot reports the pre-existing overlap as `area_entered` on the very next physics step, by which time the projectile has moved about 6.7px. The shot dies 0-7px from the muzzle. That parked state is the normal Story 1.4 contact state and becomes the steady state with Epic 2's horde. Invisible today (no damage, no art), but at Story 1.8 it means all weapon damage is dumped into whichever enemy is already body-blocking you and nothing at range is ever hit, and at Story 1.7 a shot aimed at a chosen target is still eaten by the blocker. `weapon_fired` emits at full cadence regardless, so any future muzzle-flash or audio listener announces shots that never existed. Options: (a) offset the spawn along the fire direction by roughly the enemy hurtbox radius plus the projectile radius; (b) arm the projectile after a short distance or a frame or two, ignoring overlaps until then; (c) leave it and let Story 1.8 decide when damage makes it visible. ## Dev Notes

### Conflicts between the primary sources and the five decisions (flagged, resolution chosen)

1. **`weapon_base.tscn` cannot itself be Yolk Spit.** Decision 4 said `weapon_base.tscn` is instanced under the Player, but the architecture makes `WeaponBase` the abstract parent and `ProjectileWeapon` the class that fires (game-architecture.md#Weapon Types), so an instance of the base scene fires nothing. **Resolution (user overrule, 2026-09-19):** a dedicated `projectile_weapon.tscn` owns `projectile_weapon.gd`, and that is what `player_egg.tscn` instances. A first draft proposed instancing `weapon_base.tscn` and overriding its script on the instance; the user rejected it as a footgun (a scene named for the base silently running a different script, contrary to Godot's scene-equals-script-identity convention) and asked to skip straight to the duplicate-scene pattern instead of trying the override first. The cost is the same hand-duplication accepted for `sperm_cell.tscn` in Story 1.3: `weapon_base.tscn` and `projectile_weapon.tscn` share a node structure that must be kept in sync by hand, and `weapon_base.tscn` is an unused template until a second weapon type exists. Logged in the ledger (Task 8).
2. **The architecture names the Yolk Spit class two ways.** The weapon-type tree says `ProjectileWeapon (projectile_weapon.gd)`; the file-structure tree lists `yolk_spit.gd`. **Resolution:** `projectile_weapon.gd`, per your instruction (`WeaponBase/ProjectileWeapon`). Yolk Spit is the *configuration* (the embedded `WeaponStats`), not a class, matching Story 1.3's rule against empty subclasses. The architecture's file-structure list should be corrected when convenient; not done here.
3. **`WeaponStats` carries damage-, knockback-, piercing- and upgrade-shaped fields; S6 has none of those behaviours.** Decision 2 forbids damage. **Resolution:** create the class with the documented fields exactly (do not trim it and do not invent extras), set them, and leave `base_damage`, `knockback`, `piercing`, `spread_angle`, `area_multiplier`, `projectile_count` **unread**. The architecture's WeaponBase responsibilities "Apply upgrades and modifiers" and "Handle weapon evolution" are E4 scope and are not built.
4. **`WeaponStats` duplicates two concepts it inherits.** `StatsResource` already has `damage` and `cooldown`; `WeaponStats` adds `base_damage` and `fire_rate` for the same ideas. The architecture and GDD both define it this way. **Resolution:** use `fire_rate` (attacks per second, `wait_time = 1.0 / fire_rate`) and ignore the inherited `cooldown` and `damage`; put the projectile's speed in the inherited `speed` (no new field, per AGENTS.md). Log the redundancy in the deferred ledger rather than resolving it here.
5. **The architecture's pooling sample is a global `pool_manager.gd` autoload, marked "(Future)".** Decision 3 scopes pooling to this projectile type. **Resolution:** the pool lives inside `ProjectileWeapon`, no autoload, no generic framework. The sample's mechanics also have a flaw to avoid: it "disables" a pooled object with only `visible = false` and `set_process(false)`, which leaves `_physics_process` and Area2D monitoring running. Projectiles here use `_physics_process` and an Area2D, so both must be switched off explicitly. Its "pool exhausted: expand or recycle oldest" comment is unresolved; this story chooses **skip the shot and warn once**, which cannot happen at 1 shot/s with 2 s lifetimes and a pool of 16.
6. **The architecture's `weapon_base.tscn` has `Sprite2D` and `WeaponPivot`.** The pivot exists to aim, which decision 1 removes, and there is no art. **Resolution:** omit both. Adding an unused rotation node would be building for S7.
7. **There is nothing on layer 5 to detect.** Layer 5 (`enemy_hurtbox`) is named and reserved but no node uses it: enemies have a `HitBox` (deals contact damage) and no `HurtBox`. Decision 2 has the projectile detect layer 5, which would otherwise mean it only ever expires by timer and the detection path can never be tested. **Resolution:** this story adds a **bare** `HurtBox` (`Area2D`, no script) to the two enemy scenes; S8 attaches damage handling to it. Flagged for your confirmation: the alternative is for S8 to add it, at the cost of shipping a projectile whose collision path is unverifiable in S6. It also adds a third place where enemy node structure is duplicated by hand (`enemy_base.tscn`, `sperm_cell.tscn`), deepening the existing inherited-scene deferral.
8. **Whether the projectile should be freed on hit.** The architecture says `LifetimeTimer (auto-destroy)`, i.e. free. Decision 3 requires pooling. **Resolution:** "auto-destroy" means release to the pool.

### Design decisions made by story creation

- **Pool ownership and placement.** The pool is a typed array on `ProjectileWeapon`, and projectiles are its children with `top_level = true`. Making them children keeps everything inside the weapon's subtree (no reach into the scene root, so no cross-feature reference) and frees them with the Player. Without `top_level` they would inherit the Player's transform and drag along with it.
- **`is_active`, not `visible`, marks availability.** The architecture sample uses `visible`; an explicit flag cannot be confused with a hidden-but-live node.
- **No projectile-to-weapon signal.** An `expired` signal was considered and dropped: `_acquire()` scans `is_active`, so nothing would listen. Had one been needed it would have stayed local rather than going through `SignalBus`, which AGENTS.md mandates only *between* features.
- **Firing starts at run start and never waits for enemies.** With no targeting, the weapon fires rightwards continuously so the story is observable. "Fire when an enemy is in range" is S7.
- **`player_died` stops firing.** Not in the sprint tasks; added because Story 1.5's review established that a dead player should be inert, and it is one connection. Flagged in case you would rather leave the weapon running until S7.
- **Tuning values are placeholders, not GDD values:** projectile speed 400, lifetime 2.0 s (so range 800 px), circle radii 5 (projectile) and 12 (enemy HurtBox), pool size 16. The GDD only gives `fire_rate = 1.0` and `base_damage = 10.0` as defaults.

### Critical technical gotchas

- **`_ready()` is not chained in GDScript.** `ProjectileWeapon._ready()` must call `super()`, or the timer and validation in `WeaponBase` never run. (Story 1.3's review found the same trap for `EnemyBase`.)
- **Changing `monitoring` during a physics callback must be deferred.** `deactivate()` runs from `area_entered`; use `set_deferred("monitoring", false)`. Setting it back to `true` in `launch()` **must also be deferred**: on frame 0 the queue holds `_fire_first_shot` ahead of all 16 pooled projectiles' `monitoring = false`, so a direct assignment would be overwritten and the very first shot would fly blind for its whole lifetime. Deferring puts the `true` last, where it wins.
- **Set position before enabling monitoring** in `launch()`, or a recycled projectile can report an overlap from its stale position on the first physics frame.
- **`top_level` and `global_position`.** With `top_level = true`, assign `global_position`; assigning `position` would be relative to nothing useful. The weapon's `global_position` (its own transform, inherited through the tree) is the spawn point, which is not "reading Player state".
- **Area detection rule** (as in 1.4): the projectile detects the enemy HurtBox because its mask (16) includes the HurtBox's layer (16) **and** the HurtBox is `monitorable = true`. The HurtBox has `monitoring = false` and `collision_mask = 0`; it needs neither.
- **Bitmasks:** layer 5 is `16`. Layer 4 (`player_hurtbox`) is `8`; the projectile must **not** mask it.
- **Scripted-resource `.tscn` syntax:** `[sub_resource type="Resource"]` + `script = ExtResource(...)`, never `type="WeaponStats"` (Story 1.3). An exported `PackedScene` inside the resource is written `projectile_scene = ExtResource("<id>")` with an `ext_resource type="PackedScene"`.
- **`resource_local_to_scene = true`** on the embedded `WeaponStats`, or every Player instance shares one resource (Story 1.3 review).
- **`load_steps` = resources + 1.** Recount every edited scene (`player_egg`, both enemy scenes, both new scenes).
- **No script override anywhere.** `player_egg.tscn` instances `projectile_weapon.tscn` and sets only `stats` on the instance node; the script comes from the scene itself. Do not add a `script =` line to that instance.
- **Inert projectiles must be truly inert:** `_physics_process` off, monitoring off, hidden, timer stopped. 16 idle projectiles should cost nothing per frame.
- **Do not read `SignalBus.weapon_fired` anywhere yet.** It is a fire-and-forget event with no listener.
- **UTF-8** for every file written (a cp1252 write corrupted em-dashes in Story 1.4's review). Prefer plain ASCII hyphens.
